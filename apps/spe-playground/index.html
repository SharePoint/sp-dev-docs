SharePoint Embedded (SPE) is API-only document storage built on Microsoft 365. You build the application experience; containers and files live in the consuming tenant.

In this example, a legal contract matter is the app's business object. One matter maps to one container: a content, membership, and security boundary. A real app stores the returned container ID alongside its matter record.

The contract lifecycle belongs to your app

Drafting, review, approval, signature, and renewal are business workflow stages, not SPE operations. Status, approvers, signatures, and due dates belong to your app's data and integrations. Files later live as Graph DriveItems inside the container.

    03 / Build

    From browser learning to a real application

    This is a production roadmap, not a setup wizard or generated backend. Follow the included end-to-end build sequence in order. Every learning link stays inside this playground. Reading a procedure never provisions resources.

    1. Choose the app and tenant model

      Decide single-tenant for one organization or multitenant for customer tenants. Identify the owning/developer tenant and each consuming/customer tenant: content stays in the consuming tenant. A single tenant can both own and consume an app. A trial is single-tenant and still requires registration.

      Who owns this
      Developer / architect, with tenant admins.
      Next action
      Read the in-place app and tenant planning procedure.
      Expected evidence
      A tenant ownership diagram, named admins, and a business-object-to-container mapping.

    2. Register the owning app and create its container type

      Register the Microsoft Entra application in the owning tenant. One owning app owns exactly one container type. Choose its immutable billing classification before creating the type: trial, standard, or directToCustomer (pass-through). A trial is evaluation, not production, and cannot be converted in place.

      Who owns this
      Developer / container type owner; authorized admin where required.
      Next action
      Use Create and configure a container type and Choose a billing model.
      Expected evidence
      Exact owning app ID, returned container type ID, chosen classification, and a least-privilege permission design.
      Three permission purposes, not one blanket runtime grant
      FileStorageContainerType.Manage.All
      Manage the container type in the owning tenant.
      FileStorageContainerTypeReg.Selected
      Register the type and its application grants in a consuming tenant.
      FileStorageContainer.Selected
      Runtime container and content access, constrained by type-level grants and, for delegated access, user roles.

      Separate management and registration responsibilities from routine content access. Don't request all administrative privileges in the runtime app. Use the included authentication and authorization guidance for the appropriate access mode.

    3. Configure standard billing when the developer pays

      For standard, attach Azure billing in the developer tenant. Skip this step for trial evaluation. For directToCustomer, continue to registration before customer billing activation. Changing classification requires a new container type, not an in-place switch.

      Who owns this
      Developer billing owner / type owner or authorized admin, with the required Azure subscription access.
      Next action
      Follow the in-place standard billing procedure. There is no payment or billing form in V1.
      Expected evidence
      Active developer billing configuration, subscription/resource group, cost owner, and monitoring plan.

    4. Register in each consuming tenant and verify access gates

      The owning app needs a service principal in each consuming tenant. Obtain required Graph consent, register the container type, and grant only the needed type-level application permissions. Graph consent or successful sign-in alone does not grant content access.

      Delegated operations also need the user's container membership and role. Application permissions require admin consent; delegated FileStorageContainer.Selected does not inherently require admin consent and follows tenant consent policy. Delegated registration requires a SharePoint Embedded Administrator or Global Administrator.

      Who owns this
      Developer supplies the owning-app registration flow; customer admin reviews identity, permissions, and required consent.
      Next action
      Follow the in-place registration procedure. Allow documented propagation with bounded retries/backoff and a deadline; never retry forever or show fake success.
      Expected evidence
      Registration in the intended tenant, exact app/type IDs, approved delegated/app-only grants, and the intended test user's role.

    5. Activate customer pay-as-you-go when the customer pays

      For directToCustomer / pass-through, each consuming tenant activates pay-as-you-go after registration and before container access. Standard-billed customers do not configure this customer billing profile.

      Who owns this
      Customer Billing Administrator or Global Administrator, with required Owner or Contributor access to the Azure subscription.
      Next action
      Use the in-place customer billing procedure.
      Expected evidence
      Valid consuming-tenant billing activation, a named billing owner, and an agreed cost monitoring process.

    6. Create the first container through a confidential backend

      Container creation requires a confidential client, including delegated creation. Keep credentials and token acquisition in a trusted, owned backend, never browser JavaScript or local storage. Prefer delegated user-driven access where appropriate; limit app-only access to the workload.

      Conceptual real-app architecture: browser → owned backend → Microsoft Graph → consuming-tenant storage. This is not V1's network behavior: V1 makes no service calls.

      Who owns this
      Developer / backend and security owners.
      Next action
      Implement the container request flow after registration, authorization, and applicable billing are valid.
      Expected evidence
      A real create response, stored container ID linked to the matter, and confirmed user permissions. The container ID is its Graph drive ID.

    7. Prove the file loop, then grow the app

      First real smoke sequence: create a container, create a folder, upload a small file, read and download it, then confirm user permissions. Store returned container and DriveItem IDs, not reconstructed URLs or cached short-lived download URLs.

      Who owns this
      Developer and test user, with customer admin validation.
      Next action
      Follow the in-place file operations procedure, then add only the experiences your product needs below.
      Expected evidence
      Real responses and IDs, downloaded content, allowed and denied user operations, and agreed test-data cleanup. All file and permission APIs remain docs-only in V1.

    04 / Validate & hand off

    Evidence, not just a successful sign-in

    Do this later in the explicitly authorized target tenant, using the product's normal backend and access path. A Demo result, learning acknowledgement, or successful developer-tenant test is not verified customer readiness.

    Developer: give the admin an exact handoff

    Supply publisher identity, owning and guest app IDs, container type ID/name, target tenant IDs, access modes, and the least-privilege Graph and type-level permissions with a purpose for each.

    Include your real product's redirect/sign-in locations, data and support boundaries, support contact, incident escalation, billing model and named billing owner, expected cost handling, validation plan, and rollback/test-data cleanup instructions. This page supplies none of those resources.

    Prepare the customer installation package

    Customer admin: review and validate the tenant

    Match publisher and exact app/type IDs before consent. Confirm registration, required Graph consent, type-level grants, valid billing, admin visibility, Entra member/guest identities, and each test user's resource membership/role.

    Review sharing, Conditional Access, retention, sensitivity, audit, and other tenant security/compliance expectations. Assign the appropriate SPE admin and, for pass-through, billing admin and Azure access. Stop on identity or permission mismatches.

    Follow the customer tenant setup guide

    Keep a real validation record

    Success evidence
    Record the tenant, time, exact app/type/container/item IDs, intended user and role, registration/consent/billing checks, and actual create, upload, read, and download results. Confirm customer admin visibility and approved cleanup.
    Denied-access evidence
    Test a nonmember and a read-only user's forbidden write using authorized test resources. Confirm denial, no unintended state change, and a useful app error. Test missing consent/grants, expired authentication, and billing failures where safely authorized; don't bypass the gates.
    Error evidence
    Capture actual service status/error codes, request or correlation IDs when available, timestamp, tenant, and operation in secure support records. Exclude tokens, credentials, and document content. Use bounded propagation retries, then surface unresolved failures instead of synthetic success.

    Validate customer app installation with the developer, customer admin, billing owner, and test user. No completion badges or readiness state are stored by this guide.
