Reading this guide makes no service calls, stores no progress, and proves no tenant readiness. The Demo supports only synthetic container list, create, and read operations. Everything else below is work for a separately authorized real application.

Administrative tools, identity services, Microsoft Graph, billing, and Office are not embedded or simulated here. Perform any future real setup through your organization's approved tools and owners. Never enter real IDs, credentials, tokens, or document content into the Demo.

What is SharePoint Embedded?

SharePoint Embedded is API-only document storage on Microsoft 365. Your application supplies the user experience and business workflow. SPE supplies containers and document capabilities, with content stored in the consuming organization's tenant rather than in this playground.

A container type belongs to one owning application and defines its access and billing model. Each container belongs to that type. In the example, one contract matter maps to one container; the app stores the returned container ID with its matter record. Documents inside it are DriveItems.

Review stages, due dates, approvals, and signatures belong to your application's business model. SPE is not a contract workflow or signature service. Start with the example's storage model, then try a synthetic request.

Build an app end to end

Use this order outside the Demo. Each stage needs actual evidence from the intended tenant, not a successful sign-in or an acknowledgement on this page.

  1. Plan the tenants and application ownership, including who pays.
  2. Register the owning app and create its container type with the chosen billing classification.
  3. Attach developer billing for a standard type; skip this stage for trial or pass-through.
  4. Register the type and least-privilege application grants in each consuming tenant.
  5. Activate customer pay-as-you-go for pass-through, after registration and before access.
  6. Create the first container through a confidential backend after the access gates are valid.
  7. Prove the folder, upload, read, and download loop, then validate the customer handoff.

The static Demo teaches request and state relationships without performing any of these setup stages.

Plan application and tenant ownership

  1. Choose an internal, single-tenant app or a multitenant app installed by customer organizations.
  2. Identify the owning/developer tenant, owning Entra app, and every consuming/customer tenant. A single tenant can both own and consume an app for evaluation.
  3. Map one matter to one container and decide where the app stores its business records and returned container IDs. Matter workflow data is app-owned; documents live in the consuming tenant.
  4. Name the application owner, tenant administrators, security contact, billing owner, and support owner. Record which users authenticate as Entra members or guests.

Expected evidence: A tenant diagram, app ownership decision, matter-to-container mapping, permission design, and named people responsible for setup and support.

Choose the billing classification before creating the type

trial: evaluate in the owning tenant
Single-tenant evaluation, not production. A trial lasts 30 days, permits five containers including recycled containers, and has 1 GB per container. It cannot convert in place to production.
standard: the developer pays
Attach the developer tenant's Azure subscription and resource group before use. Standard-billed customers do not activate pass-through billing.
directToCustomer: the consuming customer pays
Register the type in each consuming tenant first. That tenant's authorized billing administrator then activates pay-as-you-go before container access.

A type's billing classification is immutable. A different classification requires a new type and an explicitly planned migration, not a toggle or an unapproved delete of existing content.

Register the owning app and create its container type

  1. Prepare a Microsoft 365 tenant with SharePoint. Use a non-guest member account for Graph container type creation.
  2. Create or select the owning Microsoft Entra application. Record its application/client ID, tenant ID, supported account model, and intended redirect locations. One owning app owns exactly one container type.
  3. Separate management, registration, and runtime responsibilities using the permission model. Graph type creation uses delegated FileStorageContainerType.Manage.All; a non-guest owning-tenant user can create a type and becomes its owner without requiring an administrator role for that creation operation.
  4. Choose the billing classification before creation. Prepare the durable display name and optional behavior settings, such as sharing and Office integration, for the operations you intend to support.
  5. Have the authorized owning application create the type using the real request shape below. Record the returned type ID and owner; do not copy synthetic Demo IDs.
POST /v1.0/storage/fileStorage/containerTypes

This is a Microsoft Graph path for a future implementation, not a request executed by this page. Its payload must contain your actual owning application, display name, and selected classification.

Expected evidence: The exact owning app ID, real container type ID, selected classification, type owner, and reviewed configuration.

Attach standard developer billing

  1. For a standard type, identify the developer tenant's Azure subscription and resource group. The person attaching billing needs Azure Owner or Contributor access.
  2. A container type owner can use the SPE Visual Studio Code extension's Attach billing action for a type they own, selecting the subscription and resource group. SPE Administrators or Global Administrators can manage billing for any standard type in that developer tenant through their approved administration tools.
  3. Inspect the saved billing configuration, name the cost owner, and establish usage monitoring. If provider registration is pending, allow bounded retries; do not represent a pending billing profile as active.

Skip this developer-billing step for a trial. For directToCustomer, continue to registration before customer billing activation.

Register and authorize each consuming tenant

  1. Confirm the exact owning app, publisher, container type ID, and target consuming tenant. Registration is required even when owning and consuming tenants are the same.
  2. Install the owning application's service principal in the consuming tenant. Have the authorized customer administrator review and grant the Graph consent required for registration.
  3. Use the owning application with FileStorageContainerTypeReg.Selected and a Graph token issued for the consuming tenant. Delegated registration also requires a signed-in SPE Administrator or Global Administrator; app-only registration uses the confidential client's credentials flow.
  4. Register the type with the request below. Supply applicationPermissionGrants for the exact owning and guest app IDs, separating the delegated and app-only permissions each workload needs. Do not copy a blanket full-access grant into every component.
  5. Read and verify the resulting registration and grants. Changes can take up to an hour to propagate; use bounded backoff and an explicit deadline, then report an unresolved failure. Complete pass-through billing when applicable.
PUT /v1.0/storage/fileStorage/containerTypeRegistrations/{container-type-id}

The braces denote placeholders to replace only in the authorized real implementation. PUT replaces the complete registration payload; don't overwrite other apps' grants accidentally. A selected-property PATCH uses the registration ID and current etag for concurrency, rather than blindly replacing a registration.

Expected evidence: Registration in the correct consuming tenant, exact app/type IDs, the reviewed delegated/app-only grant matrix, and the intended test users' roles.

Activate customer pay-as-you-go for pass-through

  1. Confirm the type uses directToCustomer and registration is complete. A standard-billed customer skips this procedure.
  2. Use a consuming-tenant Billing Administrator or Global Administrator who also has Azure Owner or Contributor access to that tenant's subscription and resource group. SPE Administrator alone does not grant this billing access.
  3. In the Microsoft 365 admin center, open Setup, then Files and Content, Automate Content with Microsoft Syntex, and Go to Syntex settings. Under Syntex services for, choose Apps, then SharePoint Embedded.
  4. Complete the billing panel with the approved subscription and resource group. Confirm active billing and a named cost owner before container access. Retain the actual configuration evidence in the customer's secure records.

No billing form, subscription selector, payment collection, or activation is implemented by this guide.

Keep authentication and authorization separate

Management
FileStorageContainerType.Manage.All supports type management in the owning tenant. It is not a default runtime content permission.
Registration
FileStorageContainerTypeReg.Selected supports registration and type-level grants in the consuming tenant.
Content access
FileStorageContainer.Selected allows the relevant Graph calls, constrained by the app's type-level grants. Delegated operations additionally require the user's container membership and role: Reader, Writer, Manager, or Owner.

Application permissions require administrator consent. Delegated FileStorageContainer.Selected is not inherently admin-consent-only; follow tenant consent policy. Successful sign-in, a token, or Graph consent alone does not prove access to a container.

Use delegated access for appropriate user-driven operations and least-privilege app-only access for background workloads. Real container creation requires a confidential client even for delegated calls: browser UI → owned backend → Microsoft Graph. Keep credentials and token acquisition in the trusted backend, never in static JavaScript, the URL, logs, or browser storage. V1 contains no such backend.

Implement the first real container flow

Only proceed in an explicitly authorized test tenant after registration, access, and applicable billing are valid. The paths below are read-only learning examples for a real backend, not runnable requests in V1.

  1. Acquire the appropriate Graph token through the confidential client. Confirm the target consuming tenant and operation-specific permissions.
  2. Create one container using your real container type ID, display name, and description. For delegated creation, the creating user becomes the container Owner.
  3. Store the actual returned container ID with the app's matter record. The container ID is also its Graph drive ID.
  4. List using the required container type filter; a bare collection GET is not the supported list shape. Read the created container by its returned ID.
  5. Record actual responses or actionable errors without tokens or document content. Never convert a real failure to a synthetic Demo success.
POST /v1.0/storage/fileStorage/containers
{
  "displayName": "Authorized test matter",
  "description": "Approved test data",
  "containerTypeId": "{container-type-id}"
}

GET /v1.0/storage/fileStorage/containers?$filter=containerTypeId eq {container-type-id}
GET /v1.0/storage/fileStorage/containers/{container-id}

Replace every placeholder with returned real IDs outside this playground. Synthetic demo- IDs are invalid for these APIs. The Demo implements only its three explicitly supported synthetic shapes, not the entire real Graph contract.

Prove the first folder, upload, read, and download loop

  1. Use the returned container ID as the drive ID. Confirm content consent, type-level grants, and the delegated user's resource role before accessing files.
  2. Create an approved test folder in the container's drive, then store its returned DriveItem ID.
  3. Upload a small, non-sensitive test file to that folder with a simple content upload. Store the returned file DriveItem ID. Larger files need a separately implemented upload-session flow.
  4. Read file metadata and download content using the exact returned IDs. Compare the downloaded bytes with the approved test file.
  5. Exercise an authorized user's read/write and a nonmember's denied access. Clean up only the approved test data through the real application's owned path.
POST /v1.0/drives/{container-id}/root/children
{
  "name": "Contracts",
  "folder": {},
  "@microsoft.graph.conflictBehavior": "fail"
}

PUT /v1.0/drives/{container-id}/items/{folder-id}:/example.txt:/content
GET /v1.0/drives/{container-id}/items/{file-id}
GET /v1.0/drives/{container-id}/items/{file-id}/content

The PUT body is the test file's bytes, not the folder JSON. Handle download redirects and expiring download URLs in the real client; do not persist a short-lived URL as the file identity. No file operations or uploads are available in the Demo.

Grow only the capabilities your app supports

These are implementation and validation checkpoints, not enabled V1 features. Keep the synthetic learning app separate from a real product's runtime.

Membership and sharing

Model which matter participants can read, write, manage membership, or own the container. Implement role changes and sharing only through authorized Graph operations and permitted tenant/type settings. Validate allowed and forbidden actions with distinct test identities; an app-level grant is not the user's resource role.

Evidence: Reviewed role assignments, real permission-change results, and nonmember/read-only denial without unintended content changes.

Office launch and coauthoring

Build a supported Office launch flow for real stored Word, Excel, or PowerPoint files after the file loop works. Validate the returned launch location, user access, saved content, supported client behavior, and application return path. Check operation-specific prerequisites and licensing rather than treating a launch as proof every Office experience is available.

Evidence: Authorized users open and coauthor the intended document, changes persist, and unauthorized access fails. This guide embeds no Office client.

Document preview

Request a preview for a supported item through the authorized application. Treat returned preview locations as expiring, validate allowed origins before rendering, and show genuine unsupported-type, access, and expiry errors. A preview is not an edit operation or a durable document URL.

Search containers and files

Design the search scope for the exact containers and items the caller may access. Implement the supported Graph search flow with paging and empty/error states. Verify indexing latency and permission changes using authorized test content; never merge unauthorized results into a fallback list.

Business metadata and contract workflow

Keep matter IDs, stage, due dates, approvals, and signing state in the app's business model. Decide whether supported container properties or custom metadata help your content queries, and validate their actual limits and update behavior. A container display name is not a workflow state machine.

Security, compliance, and governance

Review customer requirements for sharing, Conditional Access, retention, sensitivity, audit, and recovery with the appropriate tenant administrators. Verify policy behavior on authorized resources. Don't infer policy configuration, a compliance guarantee, or successful recovery from a static example.

Usage, cost, and operational monitoring

Assign a cost owner and inspect actual storage, archived storage, API transaction, and egress usage for the selected billing model. Implement operation outcomes, latency, throttling handling, support correlation IDs, alerting, and approved cleanup in the real application.

Secure diagnostics should identify time, tenant, app/type/resource IDs, operation, status, and request/correlation ID when available. Exclude credentials, tokens, and unnecessary document content. Honor service retry guidance with a limit and deadline; surface unresolved failures instead of endless retries or synthetic success.

Prepare a repeatable customer installation package

The application team supplies the exact publisher, owning and guest app IDs, container type ID/name, supported tenant model, and intended consuming tenant. Add redirect/sign-in locations, requested Graph permissions and type-level grants with a purpose for each, and the expected user roles.

Include the billing model and named cost owner, support contact and escalation path, data-handling boundaries, customer-admin responsibilities, allowed/denied test plan, and rollback/test-data cleanup instructions. Never include application credentials or tokens in the package.

Customer administrator: review before consent

  1. Match the developer's publisher and exact app/type IDs against the application offered to your organization. Stop if identity or scope differs.
  2. Confirm the target tenant, required roles, service principal, Graph consent, and registration/type-level grants. Assign the test user's correct Entra identity and container role.
  3. For pass-through only, complete customer billing activation with the appropriate billing administrator and Azure access.
  4. Review governance, support, cost, and cleanup expectations. Then run the real validation sequence with the developer and authorized test user.

Validate the actual customer installation

Success evidence
Record the actual tenant, time, app/type/container/item IDs, intended user and role, registration, consent, billing checks, and genuine create/upload/read/download results. Confirm customer admin visibility and approved cleanup.
Denied-access evidence
Use approved test resources to verify a nonmember's denial and a Reader's forbidden write. Check that the failure causes no unintended change. Test missing consent/grants and authentication or billing errors only when safely authorized.
Error evidence
Retain actual service status/error codes and correlation IDs when available in secure support records without credentials or document content. Give the user a bounded next action rather than a synthetic success.

A successful developer-tenant test does not prove customer-tenant readiness. No progress, readiness state, or completion badges are stored by this guide.

Troubleshoot the right boundary

Demo storage is unavailable or corrupt
The Demo reports a local error, not Graph authorization failure. Review the browser's storage policy. Use Retry storage to reload the app's saved state; Reset Demo replaces only its synthetic seed. Reading this guide does neither.
Another Demo tab changed storage
The stale tab disables execution and clears its old results. Return to the Demo and explicitly Retry storage before continuing. Reset never touches another app's keys or Live data.
Real authentication fails
Use the real product's supported sign-in flow and verify tenant, app identity, token audience/expiry, and configured redirects with its owner. Do not paste a token into this playground.
Real access is denied after sign-in
Check registration, operation-specific Graph consent, type-level grants, and the delegated user's container role separately. Adding more runtime privileges indiscriminately is not a diagnosis.
Real billing or registration is pending
Check the selected classification, correct tenant, payer, and actual saved configuration. Apply bounded propagation retries, then return an actionable pending/error state. Missing setup never becomes successful execution.
A real request is throttled, missing, or conflicted
Retain the actual status and correlation data, verify resource IDs and access, honor retry guidance, and reconcile concurrent changes. Do not blindly replay a create request after an ambiguous response.

Return to the synthetic Demo or review the build sequence. Neither action connects to a tenant.
